## The process being walked

Baton knows nothing about promotions, purchases or leave. It knows that a form
is submitted, read by several people in turn, and decided. The process below is
the example a fresh database ships with — drawn in the admin UI, not written in
code, and the first thing a fork should throw away.

![The workflow builder](docs/screenshots/20-workflow-builder.png)

```
Submission → Department Review → Deputy Assessment → Department Decision
           → Compliance Check   → Final Approval    → Approved
```

with branches that return the file to its author, hand it back to the head, or
close it early — and email steps (the amber cards) hanging off the side of each
transition rather than sitting in it.

The demo accounts are one per part: `applicant@`, `head@`, `deputy@`,
`deputy2@`, `compliance@`, `approver@` and `records@example.org`, password
`Portal@123`, plus `admin@example.org` / `SuperAdmin@123`.

## 1 · The applicant

Sign-in is the whole of the public surface. There is no sign-up: an
administrator whitelists an address and the holder activates from an emailed
link.

![Sign in](docs/screenshots/01-sign-in.png)

The dashboard says only what this person can do next. An applicant sees their
own file; a reviewer sees their queue; an administrator sees the portal.

![The applicant's dashboard](docs/screenshots/02-dashboard-applicant.png)

The form is a wizard — one section per page, validated before each step, with a
rail showing where you are. Every question on it was defined in the admin UI.

![The first section of the form](docs/screenshots/03-form-request.png)

**Prefilled answers** come from the account. They are read-only where the portal
already knows them, and ordinary questions where it does not — so an incomplete
service record never leaves somebody unable to submit.

![Answers taken from the account](docs/screenshots/04-form-prefilled.png)

**Computed answers** are worked out from the answers beside them with a small
formula language, in the browser as you type and again on the server before
validation, because the browser is not trustworthy.

![A total computed from its neighbours](docs/screenshots/05-form-computed.png)

**Repeating groups** give the paper-form tables a real shape: each column is an
ordinary typed field, so it keeps its own validation.

![A repeating group](docs/screenshots/06-form-repeating-group.png)

**Uploads** go straight to the bucket over a short-lived pre-signed `PUT`, never
through the app server, which then confirms the object exists before trusting
the reference.

![An upload](docs/screenshots/07-form-upload.png)

Before submitting, the whole file is shown back read-only — hidden questions
omitted rather than shown blank.

![The preview before submission](docs/screenshots/08-form-preview.png)

After submitting, the applicant sees the actual graph: every step the file can
pass through, the route it has taken highlighted, and a ring on where it sits
now. Not a progress bar with invented steps — the same snapshot the engine is
walking.

![Tracking](docs/screenshots/09-tracking.png)

## 2 · The department head

The head's queue holds what is waiting on them, and only what is theirs: the
step is scoped to the applicant's own department, so the head of one department
never sees another's file.

![The review queue](docs/screenshots/10-review-queue.png)

A reviewer reads before deciding. The page opens on the file itself — the
submission and every completed review, one after another — and offers the way
through to the decision at the foot of it.

![Reading the application](docs/screenshots/11-review-reading.png)

The decision is its own tab, with the way back at the top of it. The outcomes
are the named connectors leaving this step on the canvas, so what the reviewer
sees here is exactly what an administrator drew.

![The decision](docs/screenshots/12-review-decision.png)

An outcome closes or moves an application, so it is confirmed by name. This
branch also asks the head to name a deputy, because the step it leads to is held
for one person rather than offered to a whole role.

![Confirming an outcome](docs/screenshots/13-review-confirm.png)

## 3 · The deputy the head named

The assessment step carries its own form. Reviewer answers are stored under the
step's node id, in a namespace of their own, so no reviewer can overwrite the
submission or each other.

![The deputy's assessment](docs/screenshots/14-assessment.png)

## 4 · Compliance, and the approver

Compliance reviews on a step whose questions are conditional: a second question
appears only because the answer above it says so. The same rules drive the
schema on the server.

![A conditional reviewer form](docs/screenshots/15-compliance-conditional.png)

By the time the file reaches the approver it carries everything decided before
it, in order, on one page — which is the point of reading before deciding.

![Every earlier review](docs/screenshots/16-every-earlier-review.png)

## 6 · The administrator

The history of an application is only the events that moved it. Whether an email
was queued or delivered says nothing about where the file is, so that goes to
the audit log instead.

![An application's history](docs/screenshots/19-timeline.png)

The process itself is a graph on a canvas. Validation runs as you draw, and
publishing is versioned: every publish writes a version with its memo, and any
version can be restored onto the draft.

![The workflow builder](docs/screenshots/20-workflow-builder.png)

Selecting a step opens its inspector — the role that may act, whether the step
is offered to everyone holding that role or held for one person the previous
reviewer names, whether that is narrowed to the applicant's own department, and
the outcomes that leave it.

![The node inspector](docs/screenshots/21-node-inspector.png)

Each step's questions are edited in a drag-and-drop builder. Sections are the
wizard's pages.

![The form builder](docs/screenshots/22-form-builder.png)

A field carries its type, its validation, when it applies, and — for a number —
the formula that fills it in.

![Editing a field](docs/screenshots/23-field-editor.png)

Roles are data. Create, rename, reorder and delete them, and grant each one
capabilities from a fixed vocabulary. Editing the questions on a step is a
different permission from rewiring the process.

![Roles](docs/screenshots/24-roles.png)

![A role in detail](docs/screenshots/25-role-detail.png)

Users are whitelisted, imported in bulk from CSV, edited, disabled and — when
the support question starts "it does not work for me" — impersonated, under a
rule that stops an administrator borrowing a permission they do not hold.

![Users](docs/screenshots/26-users.png)

Departments name a head and deputies. Appointing somebody grants the designated
role and removing them withdraws it, so the workflow can say "the head of the
applicant's department" without anybody maintaining a role per department.

![Departments](docs/screenshots/27-departments.png)

Emails are authored in a rich-text editor with `{{placeholders}}` hydrated from
live application data at send time.

![Email templates](docs/screenshots/28-email-templates.png)

Every action writes an audit entry with a sentence describing what happened —
filterable, exportable, and recording the administrator behind anything done
while impersonating somebody.

![The audit log](docs/screenshots/29-audit-log.png)

And the mail the run actually produced, captured by Mailpit — nothing leaves the
machine in development.

![The mailbox](docs/screenshots/30-mailbox.png)

## What is worth looking at in the code

**Applications snapshot the workflow.** Creating an application stores a copy of
the published graph, so a process can be edited and republished at any time
without changing the questions or the route of anything already in flight
([`lib/workflow/types.ts`](lib/workflow/types.ts)). The one exception is a draft
nobody has submitted: it is re-snapshotted onto the current version when its
author next opens it, and answers to questions that have gone are pruned.

**The domain is pure.** [`lib/workflow/`](lib/workflow/) — graph validation, the
transition engine, the form-to-Zod compiler, the condition evaluator, the
formula language — has no database and no React in it, which is what makes it
worth unit-testing. Seventeen unit suites cover the parts where a mistake is
silent and expensive.

**Conditional validation happens after the object parses.** Whether a field is
required cannot be known until the surrounding answers are in hand, so anything
conditional compiles optional and the requirement is added back in a
`superRefine` ([`lib/workflow/form.ts`](lib/workflow/form.ts)). The wizard
resolves against the whole form even when gating one step, which is what lets a
document in the last section depend on an answer in the fifth.

**Server actions return, they do not throw.** Every action is wrapped so
failures come back as `{ ok: false, error }` and the client can surface a toast
([`lib/actions.ts`](lib/actions.ts)). Authorisation is re-checked inside the
action rather than trusted from the page, because another holder of the same
role may have moved the application since it rendered.

**Email never blocks a transition.** A transition publishes a job to Kafka and
returns; a worker renders and sends it. A broker that is down records an
`email_failed` audit entry and the application still advances
([`lib/workflow/engine.ts`](lib/workflow/engine.ts),
[`scripts/email-worker.ts`](scripts/email-worker.ts)).

**A role's name means nothing; its designation does.** Administrators rename
roles, so departments and the workflow key off `role.designation`
([`lib/auth/designations.ts`](lib/auth/designations.ts)), and a grant a posting
made is distinguishable from one an administrator made by hand — only the former
is ever taken back.

**Styling lives in one file.** Every colour, radius and reusable layout is a
token or a component class in [`app/globals.css`](app/globals.css); call sites
use semantic utilities. The whole look retunes from there.

**Tests drive the real thing.** Nine Playwright suites run against a real
Postgres, a real S3 and a real SMTP sink — the authentication and authorisation
boundaries, both builders, administration, and the whole lifecycle: submit →
sent back → resubmit → assess → decide → check → approve, asserting the emails
each step should produce. CI runs formatting, lint, types, unit tests, a
production build and the end-to-end suite on every push
([`.github/workflows/ci.yml`](.github/workflows/ci.yml)).
